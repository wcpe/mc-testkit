# ADR-0002：本期只做「编排插件 + 脚手架模板」，不发布共享桩/机器人库

## 状态
已接受

## 背景
完整消灭各项目 E2E 重复，理想是 3 个制品：① Gradle 编排插件；② 可发布的 Kotlin 服务端桩基类库；③ 可发布的 mineflayer 机器人包。但目前只有一个被真正硬化过的 E2E 实现（N=1）。从单一用例抽象「通用桩/机器人库」，极易把该用例的特例（特定商店 GUI、特定支付方式、特定控制消息）固化进所谓"通用"框架。

## 决策
本期（第一期）**只交付两件**：①「Gradle 编排插件」（可发布）；②「`template/` 脚手架」（桩插件骨架 + 机器人内核 + 示例场景，供新项目**照抄**而非依赖）。**暂不发布**共享 Kotlin 桩基类库与共享 npm 机器人包，留待**第 2 个真实消费者**出现、暴露出真实差异后再抽（列为 P2 FR-09）。

## 理由
- 避免过早抽象：可复用 API 的规格应来自第 2、3 次真实复用的差异，而非凭想象。
- 编排（Gradle 侧）是通用度最高、收益最大、风险最低的部分，先把它抽出来即可消灭大部分重复。
- 模板让桩/机器人"开箱一致"，又保留各项目按需分叉的自由，不引入跨项目的强耦合与版本联动。

## 后果
- 桩/机器人的改进暂时靠"模板更新 + 手动同步"，会有一定拷贝漂移（可接受，待 P2 升级为发布制品时收敛）。
- 框架的「契约」集中在 Gradle DSL/任务与机器人↔桩控制协议上，而非 Kotlin/npm API。

## 备选方案
- **一步到位做 3 制品**：覆盖最全，但 N=1 抽象风险高、维护与版本联动成本大，落选（推迟到 P2）。
- **只做模板、不做 Gradle 插件**：消除不了最大块的编排重复，落选。
