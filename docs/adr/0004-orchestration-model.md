# ADR-0004：进程编排模型——前台被测后端 + 后台代理/集群 + pid 收尾 + 环境契约固化

## 状态
已接受

## 背景
一次 E2E 涉及多个进程：被测后端服务端、可能的代理、一个或多个机器人。它们的启动/停止时序直接影响测试可靠性与是否残留占端口。首个接入项目的实践还暴露了若干"经代理才会踩"的环境契约：机器人经代理 ping 拿不到后端版本会挑过新协议被踢（"Outdated server"）；后端要进 BungeeCord 模式需同时设置 `spigot.yml settings.bungeecord`、`paper-global proxies.bungee-cord.online-mode`、`online-mode=false`；某些依赖库需数据源 + Redis 正确注入才启动。`runWaterfall` 这类前台任务会阻塞且不自停，不适合做编排主体。

## 决策
采用如下编排模型，并将环境契约固化进插件：

- **前台**：被测后端以前台阻塞进程拉起；测试桩跑完场景后自行关服，回收前台线程。
- **后台**：代理与集群中的其余后端，以**后台 JVM** 拉起（复用内置模块下载的 jar），写 **pid 文件**；机器人为**后台进程**。任务结束/失败时在 finalizer/`finally` 中按 pid（`ProcessHandle`）**收尾杀掉**，保证不残留。
- **环境契约固化**（一处实现，所有消费方默认生效）：经代理时把机器人 mineflayer 协议版本**固定为后端 MC 版本**；准备阶段写好后端 BungeeCord 模式配置（`spigot.yml` / `paper-global.yml` / `online-mode`）；对依赖服务（数据源/Redis 等）做注入与缺失校验。
- **判定**：以桩写出的结果文件为权威，verify 任务读取后转为构建成功/失败。

## 理由
- 前台跑"会自停的被测后端"、后台跑"不自停的代理/集群"，时序天然正确且可由前台结束驱动收尾。
- pid + `ProcessHandle` 跨平台、可靠，避免孤儿进程占端口。
- 把反复踩的环境契约固化在框架，是本工具相对"各项目手搓"的核心价值。

## 后果
- 框架需维护这些环境契约，随上游（Paper/Waterfall 及依赖库等）变化更新（属维护者职责，集中一处）。
- 异常强杀仍可能在极端情况下留残留，需在排障文档给出清理指引。

## 备选方案
- **代理也用前台 `runWaterfall`**：前台阻塞且不自停，无法在被测后端结束后干净收尾，落选。
- **不固化环境契约、交由各消费方配置**：回到"五花八门"的老问题，落选。
- **全部后台 + 轮询日志判完成**：比"前台自停后端"更脆弱、更难判定，落选。
