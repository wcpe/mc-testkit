# ADR-0011：持久/挂起手测模式（serve 顶层块 + 非自停生命周期，补充 ADR-0004）

## 状态
已接受

## 背景
现有编排只有「自动化 E2E」一种形态（[ADR-0004](0004-orchestration-model.md)）：前台被测后端跑完场景自停 → 桩写结果文件 → verify 判 PASS/FAIL → 收尾。每条任务路径都以「桩写出结果文件」为完成信号，随后拆台。

但开发者常需要在**同款真实拓扑**（可选代理 + 后端 + 被测插件 + 依赖 + 固化环境契约）里**手动连入测试**——手测被测插件、复现要人眼看的 bug（尤其跨服 / 经代理那类自动化不好断言的）、当短期开发沙盒 / 演示。现状要么各自手搭服务端（重复、易踩环境契约坑），要么没法复用已声明的测试拓扑。缺一种「把声明拓扑拉起并**挂住**、人能连、手动停时干净收尾」的形态。

## 决策
在 ADR-0004 的自动化形态之外，**新增一种持久 / 挂起生命周期**，并经新的顶层 DSL 块声明：

1. **持久生命周期**：起后端（+ 可选代理）后**不自停、不判 PASS/FAIL**；前台**阻塞**到用户手动停（Ctrl+C 触发 JVM shutdown hook，或单独跑配套 stop 任务），按 pid **双保险收尾**后端 + 代理（与 ADR-0004 后台进程收尾同款）。**补充** ADR-0004，不推翻其自动化形态——二者并存。
2. **DSL 经新增第 5 个顶层块** `serve("name") { backend = …; via = … }` 声明持久目标（不复用 `scenario`）。`backend` 省略=默认/单后端，`via` 省略=直连。
3. **桩空闲经保留哨兵场景 id**：被测后端的桩经消费方 `dependencies{}` 注入（与 E2E 同路径），桩无场景时默认跑 `smoke` → 写结果 → 关服，会破坏「持久」。故 serve 起后端时下发**保留场景 id** `__mc_testkit_serve__`（契约常量 `McTestkitContract.SERVE_SCENARIO_ID`），并在 `template/harness` 加一个**空闲分支**：认出该哨兵即什么都不做（不驱动、不挂超时、不关服）。**对任何桩都安全**——未同步新模板的老桩遇未知哨兵 id 在 `onEnable` 抛错被禁用，**服务端照常挂起**（仅多一行报错日志）。
4. serve 仍运行在**开发者本机 / CI 可信边界内**手测——它是开发者起的**一次性手测环境**，**不是**生产托管，与 PRD 非目标「不面向玩家 / 生产服务」**不冲突**。

## 理由
- **复用全部既有积木**（provision 下载 / prepare 注入插件 / ServerLauncher 起子进程 / 代理配置 / 环境契约固化 / pid 收尾），新增面最小，符合简单优先。
- **不判定 → 不绕过结果文件自判**：serve 压根不下结论，架构不变量 §3「结果文件唯一权威」红线安全。
- **独立顶层块比塞进 `scenario` 语义更干净**：`scenario` 语义是「测试用例（bot 驱动 + 断言）」，serve 语义是「起服供人手测」（无 bot、无结果文件）。混入 scenario 会污染其语义、且 serve 与 scenario 既有字段（bot/stress/backends 判定）不相干。故宁可加一个语义清晰的新块。

## 后果
- **对外 DSL 契约从「四个顶层块」演进为「五个」**（backend / proxy / scenario / dependencies **+ serve**）。这是**加法、非破坏**变更（既有消费方 `mcTestkit { }` 声明不受影响），按 SemVer 属 **minor**。需同步 `docs/API.md` §3.1 的「四块」表述与 §3.2 任务表。
- **不破坏 [ADR-0006](0006-public-contract-conventions.md) 任何冻结项**：env 前缀（serve 复用 `MC_TESTKIT_E2E_`，不新增前缀）、任务命名约定（serve 任务 `serve<Key>` / `stop<Key>Serve` 沿用 PascalCase 派生约定）、控制协议（serve 不用）、结果文件（serve 不写 / 不判）——均不变。
- **新增一个保留场景 id** `__mc_testkit_serve__`（双下划线前后缀避免与消费方 kebab-case 业务场景名相撞）作对外契约：经 `SCENARIO` env 下发给桩、`template/harness` 据此空闲。这是**加法**（不改既有场景 id 语义），同步 `docs/API.md` §3.3。`template/harness` 加空闲分支属 FR-07 脚手架**加法**；消费方按「拷贝 + 手动同步」模型（ADR-0002）re-sync 模板才得「干净空闲」，未同步也能用 serve（老桩被禁用、服务端照常起）。
- **新增高风险维护点**：前台阻塞 + Ctrl+C / 中断收尾的**跨平台可靠性**（尤其 Windows 下 Gradle daemon 被杀时 JVM shutdown hook 是否触发）。以配套 `stop<Key>Serve` 任务**按 pid 兜底**，验收要**真机覆盖**（属测试规则点名的「进程生命周期与收尾」高风险区）。
- serve **不做世界 / 数据跨次启动持久化**（每次起全新运行目录、保留下载缓存）；要「重启留世界存档」另开 FR。
- serve 经代理时**无 bot**，故无需固定 mineflayer 协议版本（那是 bot 专属契约）；真人客户端自带版本须与后端 MC 版本匹配（文档提示）。
- 本 ADR 为 serve 模式总纲：FR-17（单后端 + 可选经代理）落核心；FR-18（集群多后端挂起）/ FR-19（持久模式可选并起 bot、人机混场）在其上**增量扩 `serve` 块**，复用本生命周期，不再各写 ADR（除非引入新决策）。

## 备选方案
- **复用 `scenario` 加法扩展（不新增顶层块，brainstorming 方案 A）**：与 FR-10/11/16（ADR-0008/0009）「加法不新增块」一致、DSL 面更小；但 `scenario`=测试用例语义会被「起服不测试」污染，且 serve 无 bot / 无断言与 scenario 字段不符。落选（用户选独立块）。
- **在既有 `e2e<Key>` 任务上加 Gradle 属性 `-Phold` 挂住**：复用任务但把「测试」与「起服」语义混于一个任务，且与「bot 驱动 + 结果文件判定」自相矛盾。落选。
- **容器 / 守护进程托管持久环境**：重型件，违反 architecture-invariants §2「简单优先、禁重型件」。落选。
