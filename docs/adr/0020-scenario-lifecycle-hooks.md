# ADR-0020：场景生命周期钩子——三个时序点与失败路径收尾保障

## 状态

已接受（扩展 [ADR-0004](0004-orchestration-model.md) 的编排模型；**不取代**其决策正文——「前台被测后端 + 后台代理/集群 + pid 收尾 + 环境契约固化」四条逐字保留）

## 背景

mc-testkit 的编排模型覆盖「下载 → 起服 → 跑 bot → 判定 → 收尾」全流程，对**自包含**的被测系统足够。但有一类被测系统**依赖外部控制面**：被测插件内的 agent 需连上一个独立进程（控制面），由它下发配置、审批身份、观测拓扑。

Lodestone 正是这类：它的 e2e 需要

1. **起一个独立的控制面进程**（Beacon，native 可执行文件，非本框架下载的 MC 平台产物）；
2. **等它就绪**（HTTP admin API 可登录，非仅端口可连）；
3. **在服务端启动后、bot 启动前**调它的 API 做初始化（登录、审批 agent 身份、下发配置）；
4. **场景结束后收尾该进程**（正常 / 失败 / 中断三路径都不能残留）。

框架当前**没有接缝**容纳这些动作：

- 就绪门只有「TCP 端口可连」与「结果文件轮询」两种（`awaitPortOpen`），应用级 HTTP 就绪无法表达；
- 没有「场景前 / 场景后」钩子——`finalizedBy` 只由框架自己的 `stop*` 任务使用，消费方无法挂载自己的收尾；
- 唯一可用的扩展点是 `backendRunDirectory`（往运行目录写文件），它解决「注入配置」，解决不了「时序敏感的动作」。

ADR-0017 开放了底层下载/运行基建，让消费方**自建整套编排**——但那是「放弃框架编排」的重路线。对只需要插入几个时序点的场景，代价过大。

## 决策

在**不改变既有编排模型**的前提下，新增场景生命周期钩子。三件事：

### 一、三个时序点（而非一个）

单一 `beforeScenario` 无法满足「控制面必须先于服务端起、审批必须在服务端就绪后做」这类需求，故按**被测系统的真实时序**设三个点：

| 钩子 | 时刻 | 典型用途 |
|---|---|---|
| `beforeScenario` | 运行目录准备完、**服务端启动前** | 起外部依赖进程、等它就绪 |
| `readyScenario` | **全部节点端口就绪后**、bot 启动前 | 依赖服务端的初始化：审批身份、造数、下发配置 |
| `afterScenario` | 场景判定之后 | 按 pid 收尾外部进程、清理 |

`readyScenario` 需要「全部节点已就绪」这一明确时刻，目前**仅集群场景**提供；在其他形态下声明会在**配置期**抛出中文异常——不静默忽略（静默忽略会让消费方以为初始化生效了，实际没跑，排查成本极高）。

### 二、钩子以**任务**承载，复用既有收尾语义

`beforeScenario` / `afterScenario` 各注册为独立任务（`before<Key>Scenario` / `after<Key>Scenario`），而不是塞进场景任务的 `doLast`：

- 独立任务可被 Gradle 的 `dependsOn` / `finalizedBy` 精确接线，时序由构建图保证，不靠手工调用顺序；
- `afterScenario` 挂 `finalizedBy`，与框架既有的 `stop*` 同层——**正常 / 失败 / 中断三路径都执行**，这是与 ADR-0004「pid 收尾，保证不残留」一致的收尾红线；
- 场景任务体内另有 `try/finally` 双保险（与既有 `stop*` 同款做法）。

`readyScenario` 不注册任务：它必须在「端口就绪门之后、bot 之前」执行，而这两个动作都在集群任务的执行体内，故由体内直接调用。

### 三、失败路径的差异化处理

两个方向的失败语义**刻意不对称**：

- **前置钩子失败即抛出**（判场景失败）：初始化没成功，后续场景跑下去只会得到误导性结果；
- **收尾钩子失败只记 warn 并继续**：收尾阶段某个钩子失败不应阻断其余资源的清理，也不应掩盖场景本身的判定失败（与既有「按 pid 收尾时进程已退出静默跳过」一致）。

## 理由

- **三时序点是需求推导的结果**，不是预留：被测系统的外部控制面天然有「起进程 → 服务端注册 → 审批」三段，压缩成一段会导致要么审批在服务端起来前做（失败），要么控制面在服务端起来后才起（注册失败且拖慢）。
- **任务承载优于体内调用**：Gradle 的接线能力（`dependsOn` / `finalizedBy`）正是为「时序 + 收尾」设计的，自己实现调用顺序会丢掉失败路径保障。
- **`readyScenario` 仅集群场景**：直连场景的后端是**前台自停**进程（ADR-0004），bot 先起、后端后起，不存在「全部节点已就绪」的时刻；经代理场景的代理先起、后端前台自停，同样没有。硬要在这些形态支持会引入不成立的时序承诺——宁可配置期报错。
- **对齐 ADR-0002 的「简单优先」**：不引入容器编排、不引入状态机、不引入插件扩展点机制；钩子只是「延时执行的用户代码 + 三个明确的挂载点」。

## 后果

- 消费方可插入时序敏感动作，无需自建整套编排（不必走 ADR-0017 的重路线）。
- 框架需保证三个时序点在**四条场景路径**（直连 / 经代理 / 集群 / 压测）上行为一致——已在实现中统一注册与接线。
- 钩子内的副作用（起进程、写文件、发 HTTP）由消费方负责其幂等性与清理；框架只保证「按声明执行」与「失败路径也收尾」。
- 钩子须可序列化（配置缓存要求动作捕获图可序列化，同 ADR-0017 的约束）：内置钩子用具名类而非 lambda（Kotlin 的 SAM 转换产物不是 `Serializable`）。

## 备选方案

- **只给一个 `beforeScenario`**：无法表达「审批在服务端就绪之后」，落选。
- **让消费方用 `backendRunDirectory` + 自建任务自行接线**：能凑出「场景前」，但**收尾拿不到失败路径保障**（框架的 `finalizedBy` 只在框架自己的 `stop*` 上），削弱 ADR-0004 的不残留红线，落选。
- **把外部控制面建模为一种 `backend`**：平台枚举是六个 MC 平台（ADR-0001/0003），塞入 native 可执行文件会破坏该枚举的封闭语义，且它不需要 MC 平台配置生成，落选。
- **引入容器编排跑外部依赖**：违反架构不变量 §2（禁止容器化），落选。
