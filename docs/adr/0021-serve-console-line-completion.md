# ADR-0021：serve 控制台采用「框架侧行级补全 + 历史」，不引入 PTY

## 状态

已接受（补充 [ADR-0011](0011-persistent-serve-mode.md) 的持久手测模式；不取代其决策正文）

## 背景

`serve` 挂住期间可以直接在 Gradle 终端输入服务端控制台命令（FR-17 的控制台命令增补，见 [API.md §3.2.1](../API.md)）。但用户实测两个症状：

1. **按 Tab 没有补全**——原版服务端控制台（JLine）的 Tab 补全会给出命令名与参数候选，这里什么都不发生；Tab 甚至会把制表符混进命令里，让服务端收到 `hel\tlo` 这样的未知命令；
2. 原版控制台的其它交互能力（↑/↓ 历史、←/→ 行内编辑）同样缺失。

要判断能修到什么程度，必须先确定**输入到底以什么形态到达构建进程**。实测（伪终端 + 真实 Paper 1.20.1，2026-09-26/27）：

| 事实 | 证据 |
|---|---|
| 构建跑在守护进程里，**没有终端** | 任务内 `System.console()` 为 `null` |
| 终端**按行**投递、自己回显、自己处理退格 | pty 下喂 `abc\tdef\n` → 构建侧原样读到该行（含 Tab 与 `ESC[A`）；喂 `pr` + 两个退格 + `\n` → 构建侧只读到 `\n`（退格被终端消掉） |
| 服务端自己也用不上它的补全 | 管道 stdin 下 Paper 打印 `Advanced terminal features are not available in this environment` |
| 服务端能给出命令表 | Paper 控制台 `help` **一次**打印全表（1.20.1 实测 91 条含别名）；BungeeCord 26.1 与 Velocity 3.4.0 的控制台**没有** help 命令 |

也就是说：**逐键补全与行内编辑在 Gradle 控制台下达不到**（拿不到按键、也改不了终端模式），但「Tab 落在整行里」这一事实可以被我方利用——补全可以由框架在收到整行后完成。

## 决策

serve 控制台的能力由**框架在行级实现**，不引入 PTY / 原生依赖：

1. **Tab = 补全请求**（不再把制表符当命令内容下发）：
   - 候选唯一 → 补全并把补全结果下发（等价 shell 里「Tab 补全 + 回车」）；
   - 多候选 → **只列候选、不下发**（用户正是在问"有哪些"）；
   - 无候选 → 若 Tab 在行尾，照常下发用户敲的内容（等价 shell 里「Tab 没补到 + 回车」）；Tab 之后还有内容则不猜、不下发（不丢用户已敲的字）。
2. **候选来源 = 服务端命令表 + 本控制台历史**：
   - 命令表：serve 就绪后往服务端控制台发一条 `help`（平台若分页则继续翻页，直到没有新命令），输出落日志并解析命令名；该段日志构成**隐藏窗口**——控制台回放窗口之前的起服日志、从窗口之后继续跟随，于是几十行 help 不刷屏而 Tab 立刻有权威候选。平台没有 help 命令时（BungeeCord / Velocity）如实退化为只用历史，不伪造候选。
   - 参数位置（已敲空格）的候选退化为「你自己用过的整行」：参数补全要靠服务端自己的命令树，管道 stdin 下它给不出。
3. **↑/↓ = 历史**：调出并下发（本终端无法把历史塞回编辑缓冲，故取 shell 语义「↑ + 回车 = 重跑」），并打印调出的是哪一条。历史跨轮次持久化到结果目录（与进程台账同处，不随运行目录清理）。
4. **其它控制序列（←/→/Home/End/Delete）= 不下发 + 中文说明**：原样下发只会让服务端报未知命令，说清限制比让用户猜好。
5. **服务端 `help` 输出保持可见性可选**：它照样写进运行目录日志（排障与追溯需要），只是不回放到控制台。

## 理由

- **能达成的最高保真度**：在「只拿到整行」的前提下，补全、历史、命令透传都能给到；行内编辑与参数补全确实要不到，如实说明而不是假装有。
- **零新依赖**：PTY 路线要引原生库（pty4j 之类），Gradle 插件被消费在 Windows / Linux / macOS / 容器 CI 上，原生库的解压与平台适配是新风险面；而按本 ADR 的取舍，PTY 换来的仍然只是「更晚才出现的补全结果 + 双回显」，收益远小于代价。
- **候选不写死**：命令表来自服务端自己（含原版 + Bukkit + 插件命令与别名），不维护一张随 MC 版本与插件变化的静态表——静态表既会漂移，也会把「框架认识哪些命令」变成与真实服务端不一致的第二真源。
- **失败不阻断**：抓取命令表失败只是「没有候选」，serve 照常起服挂住（补全是便利能力，不是必需能力）。

## 后果

- serve 控制台的补全**依赖于服务端提供 `help`**：Paper/Spigot/Folia 有（后端 serve 的常见形态），BungeeCord/Velocity 没有（此时只用历史命令，日志与文档都写明）。
- `serve<Key>` 就绪阶段会多一次 `help` 往返（约数百毫秒）与对应日志写入；控制台看不到，运行目录日志里可查。
- 历史文件（`<结果目录>/serve-console-history-<serve>.txt`）与进程台账同处，属可安全删除的中间产物。
- 行内编辑（←/→）与参数补全**永久不提供**，除非将来 Gradle 改变终端输入模型；文档与提示文案要一直说清楚这件事。
- `e2e*` 等自动化任务**不接线**这套交互（保持结果确定性）——与 FR-17 的既有边界一致。

## 备选方案

- **给服务端分配 PTY，让服务端自己的 JLine 控制台工作**：补全与参数补全由服务端算，最忠实；但 (a) 新增原生依赖与平台适配；(b) 用户侧仍是按行转发，会出现「按键只在回车后才被服务端看到、回显重复、补全结果滞后」的怪异体验；(c) 服务端会把交互式提示符与重绘写进日志。落选。
- **`inheritIO()` 把真终端交给服务端**：Gradle 的构建进程在守护进程里，其 stdin 是客户端转发的管道而非终端，`inheritIO` 交出去的仍是管道；且会丢掉「日志落运行目录」这一既有契约（排障真源）。落选。
- **经 RCON 取命令表**（Paper 支持 RCON，输出不经日志、无刷屏问题）：只在 Bukkit 系可用（代理无 RCON），要在 serve 里额外开一个监听端口与随机口令，属为便利能力扩安全面；且与日志路线并存会变成两套机制。落选。
- **框架内置一张「常见控制台命令」静态表**：会在 MC 版本 / 插件变化后漂移，且与真实服务端不一致时给出错误候选。落选（坚守「真源在服务端」）。
- **在框架侧模拟行内编辑**（解析整行里的 `ESC[D` 等序列自行改写内容）：终端已把转义序列按字面回显给用户，屏幕与实际执行内容不一致，比不支持更容易误导。落选。
