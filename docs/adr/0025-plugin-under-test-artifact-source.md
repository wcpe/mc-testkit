# ADR-0025：待测插件产物来源可配置（`pluginUnderTest(from = …)`，框架自动接线）

## 状态

已接受（扩展 [ADR-0015](0015-maven-coordinate-plugin-dependencies.md) 的「依赖声明维度」与 [ADR-0006](0006-public-contract-conventions.md) 的对外契约；**不取代**其决策正文——「不做 `pluginUnderTest` 的坐标形式」「任务命名 / env 前缀冻结」等条款逐字保留）

## 背景

`dependencies { }` 的待测插件此前只有两种表达：**环境变量名或路径**（`pluginUnderTest = "…"`，运行期解析）与**不声明**（自测模式：框架按契约默认取本模块 `jar` 任务产物，并自动把 `prepareE2e<Key>` / `e2e<Key>` / `serve<Key>` 接到 `jar` 上）。两者都建立在「产物就是这个模块的 `jar` 任务，或是一个运行期才知道的路径」这一前提上。

有一类消费方不满足该前提：**用 shadow 插件产出 fat jar**，待测产物是 `shadowJar` 而不是 `jar`。它们的 e2e 实际上跑 `shadowJar` 的产物，但 DSL 无法表达「产物来自哪个任务 / 哪个文件集合」，于是只能自己打补丁——真实消费者 TabooLib 的 `e2e-harness` 即如此：

- `jar { enabled = false }` 关掉普通 jar，避免自测模式取到错的那个产物；
- `afterEvaluate { tasks.matching { it.name.startsWith("prepareE2e") }.configureEach { dependsOn(shadowJar) } }` 手工补任务依赖，否则全新检出下 prepare 的前置预检会因产物尚未产出而失败。

这段补丁有两个固有缺陷：

1. **匹配任务名**是脆弱接线——任务名靠字符串前缀猜，框架一旦调整注册形态就可能静默失配；
2. **`jar { enabled = false }` 是个反直觉的前置条件**：关掉一个框架并不必需的任务，只为让自测模式不选中它；消费方得先知道自测模式的存在与实现细节才能写对补丁。

「待测产物从哪来」是被测系统的事实，不该由消费方用任务名匹配与禁用无关任务来间接表达。

## 决策

在 `dependencies { }` 内**加法新增**产物来源形式：`pluginUnderTest(from = …)`，与既有字符串形式并列、**互斥**。四件事：

### 一、声明形态：接受 `project.files(…)` 可接受的任意输入

`pluginUnderTest(from = source)` 的 `source` 按 Gradle 的 `FileCollection` 语义接受任意输入——`TaskProvider`（如 `tasks.named<ShadowJar>("shadowJar")`）、任务输出、`project.files(...)` 可包装的其它来源皆可。**推荐传 `TaskProvider`**：只有携带任务信息的形式才能让框架建立产物依赖（见决策三），传普通文件路径则只是「路径来源的另一种写法」，拿不到自动接线。

### 二、语义：从该来源解析出**恰好一个** jar 作为待测插件

不引入「多产物」「产物选择器」概念：待测插件在契约里本就是**单个** jar（注入目标名固定 `plugin-under-test.jar`）。来源解析出的 jar 不是恰好一个时**配置期中文报错**，不静默取首个——静默会让消费方以为跑的是自己想的那个产物。

### 三、自动接线：消费方不再写任何 `dependsOn`

声明来源后，框架把 `source` 携带的产物任务**自动接**到需要待测产物的任务上（prepare / e2e / 经代理 / 集群 / 压测 / serve 各形态，与自测模式既有的自动接线同一批注册点）。这正是本次要消除的补丁：消费方不必再按任务名匹配、也不必再禁用 `jar`。

### 四、与既有形式互斥，且在配置期以中文错误失败

同时声明 `pluginUnderTest = "…"` 与 `pluginUnderTest(from = …)` 时**配置期报中文错误**，不静默取其一。两种形式的含义不同（一个是运行期解析的名字/路径，一个是构建期确定的产物来源），静默取其一会让另一处声明看似生效实则被忽略——与 [ADR-0020](0020-scenario-lifecycle-hooks.md) 拒绝静默忽略 `readyScenario` 同一条原则。

### 五、优先级不变

- **执行期 `MC_TESTKIT_E2E_PLUGIN_UNDER_TEST_JAR` 仍最高**：声明来源后该环境变量仍可覆盖（CI / `GradleRunner` 注入用），与既有语义一致。
- **未声明任何形式时仍走自测模式**：回退本模块 `jar` 任务产物并自动接线，行为不变。
- 声明了产物来源的任务则**不再是自测模式**（不再回退 `jar`、不再按自测模式报「先执行 `gradlew jar`」的指路错误）。

## 理由

- **让声明贴近事实**：消费方的待测产物来自 `shadowJar` 是构建事实，把它写成「`FileCollection` 输入」比写成「匹配任务名 + 禁用无关任务」的补丁更直接，也更能被框架校验。
- **接线由构建图保证**：任务依赖由框架建立，消费方不必再猜任务名，也不会因框架调整注册形态而静默失效（补丁式 `tasks.matching { it.name.startsWith(...) }` 的失效是静默的）。
- **互斥报错优于优先级仲裁**：两种形式的解析时机与语义都不同，给一个隐含优先级会让「为什么跑的不是我声明的产物」变成排查题；配置期直接失败，问题在最便宜的时刻暴露（口径同 ADR-0015 的「配置期校验坐标」）。
- **不推翻既有契约**：这是**纯加法**——既有两种表达（字符串声明、自测模式）语义与优先级逐字不变；产物来源是第三条声明路径，不涉任务命名、env 前缀、控制协议与结果文件格式（SemVer minor）。
- **消费方是具体的**：本次有明确消费方（TabooLib `e2e-harness` 的 shadow fat jar 形态），不是为假想需求预留空壳（守 `.claude/rules/scope-discipline.md`）。
- **与「不做坐标形式」不冲突**：坐标形式解决的是「制品**从哪个仓库**取」（ADR-0015 记「待真实需求再加」），产物来源解决的是「制品**由哪个任务产出**」——前者跨网络解析，后者是本地构建产物，两个维度正交（同 [ADR-0016](0016-maven-coordinate-server-jars.md)「`mavenServer` 只决定 jar 从哪来，不影响 `version`」的分维思路）。

## 后果

- **正面**：shadow / 自定义产物形态的消费方可删掉 `jar { enabled = false }` 与 `afterEvaluate { tasks.matching … dependsOn … }` 两处补丁，待测产物来源变成一条可校验声明；「产物未产出就先预检」这类接线遗漏在框架内被一次性解决，不必每个消费方各写一遍。
- **约束**：
  - 来源必须解析出**恰好一个** jar，否则配置期中文报错；多产物场景不在本期范围内。
  - 传普通文件路径（无任务信息）时无法自动接线，消费方仍需自行保证产物先于任务产出。
  - `FileCollection` 是 Gradle 原生对象，本形式只在**配置期**消费，不进入任务动作捕获图（配置缓存约束同 ADR-0015/0017：动作闭包绝不捕获 `Project` 或 Gradle 对象）。
- **不改动**：任务命名、env 前缀、控制协议、结果文件格式；`pluginUnderTest = "…"` / `plugin(...)` 语义与优先级不变；未声明任何形式时的自测模式行为不变；v1 **仍不做** `pluginUnderTest` 的坐标形式。

## 备选方案

- **只写文档，教导消费方继续用 `afterEvaluate` + `tasks.matching` 补丁**：零实现成本，但把「按任务名匹配 + 禁用 `jar`」固化为对外指导——补丁失效是静默的，且消费方要理解框架内部的自测模式才能写对；真实消费者已经写了这个补丁正是「现有表达不够」的证据，文档化不解决该缺口。落选。
- **把自测模式的默认产物从 `jar` 改为「可配置的任务名」**（如新增一个属性指定默认产物任务名）：看起来更小，但它只解决「换成 shadowJar」，仍把「来源」限制为一个任务名，且与「自测模式默认为本模块 `jar`」的既有契约纠缠——改默认会把语义从「产物来源」变成「自测模式的候选任务」。落选。
- **支持 Maven 坐标形式**（`pluginUnderTest(coordinate = "…")`）：解决的是另一件事——制品不随公开仓库分发时经仓库解析（ADR-0015 已为 `plugin(...)` / `mavenPlugin(…)` 做过），与「本地构建产物从哪个任务来」正交。本次有真实需求的是产物来源，坐标形式仍按 ADR-0015 记的「待真实需求再加」。落选。
- **给 `pluginUnderTest` 加「多产物」或顺序语义**：待测插件在契约里是**单个** jar（注入目标名固定），引入列表会把「恰好一个」的校验推给运行期、并让「跑的是哪个产物」变得不明确，收益不抵概念成本。落选。
