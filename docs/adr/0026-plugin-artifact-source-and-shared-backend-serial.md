# ADR-0026：依赖插件产物来源（`plugin(from = …)`）与共享后端场景自动串行

## 状态

已接受（扩展 [ADR-0025](0025-plugin-under-test-artifact-source.md) 的「产物来源」维度到**依赖插件**；并补齐 [FR-04](../PRD.md) 任务自动编排在多场景共享后端下的缺口。不取代任何既有决策正文）

## 背景

以某个真实消费方接入时，暴露两个框架缺口。两者都不是消费方能用 DSL 正确表达的，只能靠消费方自写任务脚本绕过——那正是 [scope-discipline](../../.claude/rules/scope-discipline.md) 要防的漂移。

### 缺口一：`plugin()` 无法表达产物来源

ADR-0025 已为**待测插件**引入 `pluginUnderTest(from = …)`，但**依赖插件**仍只有字符串形式：

```kotlin
fun plugin(envVarOrPath: String)   // 只有这个
```

E2E 桩插件常是独立 Gradle 子工程（自带 `settings.gradle.kts`，不在主构建的 project 树里），它的 jar 由子工程自己的 `jar` 任务产出。消费方因此只能写死路径：

```kotlin
plugin("e2e/harness/build/libs/harness-1.0.0-SNAPSHOT.jar")
```

后果是**必须先人工构建桩**，否则注入的是旧 jar 或根本不存在的路径。消费方要么在 CI 里多写一步 `cd e2e/harness && ./gradlew jar`，要么写任务依赖补丁——与 ADR-0025 要消除的那类补丁完全同构。

### 缺口二：多场景共用同一后端时互相踩踏

一个后端名对应**唯一**的运行目录（`run-<backendName>`）与端口。若两个场景共用该后端，且消费方在同一条命令里请求它们：

```bash
./gradlew e2eSmoke e2eMobSpawnWithBot e2eCommandCastWithBot
```

会稳定失败：

- `FileAlreadyExistsException`：多个 `prepareE2e<Key>` 并发往同一运行目录复制服务端运行库；
- 端口绑定失败：两个场景同时起服务端抢同一端口。

这与 `org.gradle.parallel` 开关无关——Gradle 本来就会并行调度**没有依赖关系**的任务。框架此前只在 `versionMatrix` 展开的场景里挂了串行链（按版本隔离后端），**手写 `scenario()` 时完全没有这层保护**。消费方无法从 DSL 表达「这些场景要串行」，只能自写 `mustRunAfter` 编排——同样是越界。

## 决策

### 一、`dependencies { }` 加法新增 `plugin(from = …)`

与 ADR-0025 的 `pluginUnderTest(from = …)` 同构：接受 `project.files(…)` 可接受的任意输入，**推荐传 `TaskProvider`**，框架据此自动建立产物任务依赖。

与既有的 `plugin(envVarOrPath)` **并列而非互斥**：依赖插件可以有多个，各自来源形式独立，可以混用。

产物来源在配置期已解析为具体文件，执行期不再查环境变量；缺失时进统一的中文报错（与路径 / 坐标形式的缺项一起列出）。

### 二、共用同一后端的场景自动串行

按「场景 → 所属后端」归组（显式 `backend` > 经代理路由的第一个后端 > 首个后端），**组内**只挂一条规则：

> 后声明场景的**全部运行期任务** `mustRunAfter` 前一个场景的**全部运行期任务**。

其中「运行期任务」= 会写同一后端运行目录 / 占同一端口 / 依赖其进程状态的任务：`prepareE2e<Key>`、
`launch<Key>Bot`、`e2e<Key>`、`e2e<Key>WithBot`、`e2e<Key>Cluster`、`e2e<Key>Stress`，以及声明了 `via` 时的
`e2e<Key>Via<Proxy>`。各场景形态注册的任务不同，未注册的名字在落边时按 `project.tasks.names` 过滤。

取**全组合**而非只牵 `prepare`，是因为踩踏不止发生在两个 prepare 之间：只按 `prepare → prepare` 串行时，
`./gradlew e2eA prepareE2eB` 里 B 的 prepare 仍会在 A 的服务端运行期间清空同一运行目录（
`cleanRunDirPreservingRuntimeCaches`）。全组合让「B 的任何一步都不与 A 的任何一步重叠」，是唯一无缝隙的规则。
机器人也在这个集合里，故「后一个场景的机器人要等前一个场景跑完」由同一条规则覆盖——否则它会提前启动，
就绪超时先于自己的服务端到来而退出。

**组间不加任何约束**：不同后端有独立目录与端口，可以安全并行。

顺序边的计算抽成纯函数 `sharedBackendOrderEdges`（返回「任务名 → 它须排在其后的任务名」），便于穷举测试
——`mustRunAfter` 是只写 API 读不回来，`--dry-run` 的输出顺序也只反映依赖边，故不能靠 TestKit 间接推断。

## 理由

- **一致性**：缺口一是 ADR-0025 的机械扩展，同一套 `FileCollection` 语义与自动接线模式，消费方无需学新概念。
- **安全默认**：缺口二把「共享后端的场景必须串行」变成框架保证而非消费方纪律。踩踏症状（文件冲突 / 端口占用）与消费方代码毫无关系，却只能由消费方排查，属框架该兜的底。
- **不牺牲并行**：只对共享同一后端的场景加约束，版本矩阵那种「每版一个后端」的形态仍可全速并行。
- **可测试**：把顺序编排抽成纯函数，使「该串的串了、不该串的没串」可被穷举断言，而不是靠观察构建输出。

## 后果

- 消费方不再需要为「桩是独立子工程」写 `dependsOn` 补丁，也不再需要 `cd` 进子工程手工构建。
- 同一条命令请求多个共享后端的场景可正常执行（串行），耗时相应增加——这是正确性的必要代价。
- 组内串行是**整段**的：连只请求后一个场景的 `prepareE2e<Key>` 也会先等前一个场景跑完。这是保守选择——
  单跑 prepare 的耗时远小于重跑一次被踩踏的 E2E。
- 任务命名、env 前缀、控制协议、结果文件格式**均不变**。
- `plugin(...)` 的字符串形式语义与优先级不变（纯加法，SemVer minor）。

## 替代方案（均未采纳）

- **每个场景自动分配独立后端**：可彻底消除冲突并保留并行，但会把消费方显式声明的后端数量悄悄放大（3 个场景变成 3 个 2GB 服务端），违反「不为未来预留」与资源常识；且与消费方「我要测的就是这一个后端配置」的意图相悖。
- **运行时对运行目录加文件锁**：只能把并发变成阻塞等待，仍会二次起服抢端口，且把问题推到更晚才暴露。
- **要求消费方改用 `versionMatrix`**：矩阵按版本展开，不解决「同一版本多个场景」这一常见形态。
