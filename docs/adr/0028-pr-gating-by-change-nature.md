# ADR-0028：PR 门禁按变更性质分级——发版与纯文档可直推，代码修复 / 功能仍必须走 PR

## 状态
已接受（取代 [ADR-0018](0018-ci-release-and-pr-gating.md) 的决策 1「改动必须经 PR」，其余决策不变）

## 背景
[ADR-0018](0018-ci-release-and-pr-gating.md) 把 `master` 的准入收紧为「一切改动（功能、修复、重构、文档、发版）都必须经 PR + 必需检查全绿 + squash 合并」。它解决的真问题成立：曾出现发布提交本身在 ktlint 上失败、版本处于门禁红状态，以及「直推绕过验证门」。

实践一段时间后，这条**统一规则对两类变更是明显过重的**：

1. **发版提交**：一次发版要改的只有两处——根 `VERSION` 与 `CHANGELOG.md` 的段落定稿，且**没有任何代码改动**。但走 PR 意味着：开分支 → 开 PR → 等 `构建与测试（插件）`（约 5.5 分钟）+ `Windows PTY 构建与测试`（约 6 分钟）+ `静态检查` → squash 合并 → 才能打 tag。而**打 tag 后的 `release.yml` 本来就会再跑一遍 `./gradlew build` 兜底**（ADR-0018 决策 3）。也就是说，PR 这一轮 CI 对发版而言是**几乎完全重复的验证**，代价是每次发版多等 6~7 分钟与一条空分支的生命周期。
2. **纯文档更新**：只改 `*.md`（错别字、措辞、引用链接失效、补充说明），不触碰任何代码 / CI 配置 / 构建脚本。这类改动**天然不可能让构建变红**，却同样要等 6 分钟构建 + 开一条分支。

而被这条规则真正要挡住的——**代码改动**（`feat` / `fix` / `refactor` / 构建脚本 / CI 工作流）——恰好是验证门真正有价值的地方：它们会改变插件行为或流水线行为，必须有 CI + 评审。

因此要把「一刀切」改成「按变更性质分级」，在**不放弃代码改动门禁**的前提下，给这两类低风险变更去掉流程税。

约束与驱动因素：

- `master` 的验证门（`构建与测试（插件）` / `静态检查（模板 bot）`）必须**继续对代码改动强制**——ADR-0018 要解决的门禁绕问题不能回潮。
- 发版已有独立的兜底：`release.yml` 打 tag 后会重跑 `./gradlew build` 并校验 tag 与 `VERSION` 一致，**发布错误版本的窗口由它兜住**，不依赖 PR。
- 仓库目前是单人主导维护（PR 无 human review 要求，`required_approving_review_count: 0`），PR 的价值主要来自 CI 与变更留痕，而非多方评审。
- **`enforce_admins: true` 与「允许直推」互斥**：该开关让分支保护对管理员同样生效，直推会被服务器拒绝（`GH006: Protected branch update failed`）。要落地本决策必须同时把它关掉。

## 决策
把 `master` 的准入从「一切改动必须走 PR」改为**按变更性质分级**，并把这条分类写进校验点：

1. **以下两类可直接推 `master`（免 PR）**：
   - **发版提交**：只含根 `VERSION` 的版本号 bump + `CHANGELOG.md` 的段落定稿（`## [未发布]` → `## [X.Y.Z] - YYYY-MM-DD`），推荐单条提交 `chore(release): 发布 X.Y.Z`。
   - **纯文档更新**：只改 Markdown 文档（`docs/**`、`*.md`、`.claude/rules/*.md`），不触碰任何代码、构建脚本、CI 工作流、配置。
2. **其余一切改动仍必须走 PR**，且必需状态检查全绿 + squash 合并——明确包含：`feat` / `fix` / `refactor` / `perf` / `test` / `build` / `ci` 类型，以及任何触碰 `src/**`、`*.gradle.kts`、`.github/workflows/**`、`bot-core/**`、`harness-core/**`、`template/**` 的提交。**「顺手带一点代码」不算纯文档**：一个提交里只要含代码文件，就退回 PR 路径。
3. **合并方式不变**：走 PR 时仍**只允许 squash**、`required_linear_history` 保持开启；直推的提交本身即一条线性提交，不破坏线性史。
4. **必需检查仍是 PR 的门禁**，其对 `master` 推送的触发不变（`ci.yml` 仍监听 `push: branches: [master]`）——**直推后 CI 照样跑**，只是它不再是「合并的前置条件」，而是「事后告警」。这是有意接受的代价：直推的改动若让 CI 变红，由维护者立即修复（发版类改动本身不含代码，风险低；文档类改动不会影响构建）。
5. **发版流程的其他环节全部不变**：仍由 `release.yml` 在 tag 推送时校验 tag 与 `VERSION` 一致、重跑 `./gradlew build`、发布到 maven.wcpe.top、建 Release（正文 `--generate-notes` 从 PR 生成，ADR-0019）。**禁止本地 `./gradlew publish` 发正式版、禁止手工建 Release**——这两条不变。

### Release 正文的影响（须知晓）
`--generate-notes` 只汇总**该 tag 区间内合并的 PR**。直推的提交（发版提交、纯文档提交）**不会**出现在 Release 正文的 PR 列表里——这是本决策的直接后果。判定：**可接受**。
- 发版提交本身（bump `VERSION` + 定稿 CHANGELOG）不该成为「本版本改了什么」的条目——它是元数据，不是变更内容。此前走 PR 时它反而会出现在正文列表里（如 v0.17.1 的正文含 `chore(release): 发布 0.17.1 (#25)`），属于噪声。
- 纯文档改动面向读仓库的人，真源在 `CHANGELOG.md` 与文档本身，不需要在 Release 正文里单独列出。
- **版本内容仍完整**：真正的代码变更（`feat` / `fix` …）照旧走 PR，照旧被汇总进正文。

## 理由
- **验证强度与变更风险对齐**：代码改动过完整 PR 门禁（构建 + 风格 + Windows PTY + 评审留痕）；发版与文档改动跳过一条**重复的**构建，风险由「不碰代码」与「release.yml 的兜底 build」双重覆盖。
- **去掉的是一段重复劳动，不是一道校验**：发版的构建校验在 `release.yml` 里**照跑**，且那里还会额外校验 tag 与 `VERSION` 一致（PR 路径反而没有这项）。
- **流程税与改动价值成比例**：发版本该是「一条提交 + 一个 tag」两分钟的事；此前要 6~7 分钟等一轮与发布重复的 CI。
- **没有削弱 ADR-0018 的核心**：它防的是「代码绕过验证门进 master」，本决策对该类改动**一字未松**，`enforce_admins` 关闭只是解除对**维护者本人**在低风险路径上的阻塞，而非开放所有人任意直推（分支保护其余项——禁止强推、禁止删分支、必需检查、线性史——全部保留）。

## 后果
- **正面**：发版收敛为「提交 → 打 tag」两个动作；文档纠错可以立即落地；PR 列表回归「每条都是值得评审的代码变更」。
- **约束 / 代价**：
  - **必须关掉 `enforce_admins`**（改为 `false`），否则直推被服务器拒绝。这也意味着**管理员在技术上可以直推任何东西**——本决策的分级**靠纪律与文档约束，不再由服务器强制**。这是本决策最实质的让步，须自觉遵守：**判断标准只有一条——这个提交是否触碰了代码 / 构建 / CI**。
  - **直推后 CI 仍会跑，但为事后告警**：红了要立刻修，不能「反正已经进 master 了」放着。
  - **squash 的 PR 标题仍是 Release 条目**，写清「改了什么 + `(#n)`」的要求不变（ADR-0019）。
  - 若将来引入多人协作 / 需要人工评审（`required_approving_review_count > 0`），应重新评估本决策——届时应恢复 `enforce_admins: true` 并收紧为全 PR。
- **不做**：
  - 不放开 `feat` / `fix` 等代码类提交的直推（哪怕只有一行）——「一行代码」正是验证门最该覆盖的场景。
  - 不做「按提交消息前缀自动判定能否直推」的工具化校验——GitHub 的分支保护不支持按路径 / 前缀放行，硬做需要自建 CI 门禁或 rulesets，**YAGNI**；本阶段靠流程纪律。
  - 不改 Release 正文生成方式（仍 `--generate-notes`，ADR-0019 不变）。

## 备选方案
- **维持「一切改动必须走 PR」**（ADR-0018 原样）：门禁最强、零纪律依赖。落选原因：对发版与文档这两类**结构性低风险**变更收取与代码改动同等的流程税，且发版那轮 CI 与 release.yml 的验证完全重复。
- **用 GitHub Rulesets 按路径放行**（如只允许 `docs/**` 直推）：能保留服务器强制，粒度最细。落选原因：rulesets 的绕过规则按**角色**而非按路径，真正的路径级放行需要拿掉该路径的必需检查——而必需检查是整分支级别的，做不到「只对 docs 免检」；真要实现得自建一个校验 job，属过度工程。
- **发版改为「合并即自动发版」消掉 tag 手工步骤**：需长期 PAT（`GITHUB_TOKEN` 建的 tag 不触发 workflow，ADR-0018 已论证），且自动推断版本号脆弱。落选，与本决策正交。
- **只放开文档、不放开发版**：发版的 PR 反而更冗余（release.yml 已兜底构建），且发版频率低于文档纠错、解锁频次少。落选。
