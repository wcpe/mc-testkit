# ADR-0029：机器人与钩子进程的输出字节预算，及结果目录的输出所有权

## 状态
已接受（取代 [ADR-0009](0009-multi-bot-per-scenario.md) 决策 4 中「bot 按 pid 文件收尾」的收尾方式：bot 改由进程监管与进程台账收尾，pid 文件只供排查；ADR-0009 的其余决策不变）

## 背景
- bot 与场景钩子后台进程的输出原先用 `ProcessBuilder.Redirect.appendTo(File)` 交给内核直接写文件：JVM 不经手，既没法计数、限流，也没法在越限时中断。一次本地事故里 9 个 bot 日志合计写到 130 GiB，直到磁盘写满才停。
- 后台进程收尾此前只靠 pid 文件与停任务。构建结束时仍在跑的进程、根进程退出后仍握着输出管道的子孙进程，都可能在构建之外继续写结果目录。
- 结果目录跨构建复用。上一次构建若没收尾（被强杀、被外部超时杀掉），它的进程可能还在写，本次构建照常接手就会和它并发写同一目录。
- 初版实现在评审与实测里暴露出几个问题：
  - 「上一次不是 `CLOSED_OK` 就拒绝接手」让连跑矩阵里一格失败后，后面所有格都在准备阶段被拒；停任务同样被拒，用户想清理都做不到，报错也没有恢复指引。
  - 单个日志默认 8 MiB 且越限即判失败：实测一个 bot 长跑 610 秒写 20.7 MB，正常负载就会触发；一个话多的 bot 还会连带停掉其他正常运行的进程。
  - 日志与受监管进程各有 128 个的固定上限：文档里的压测示例（2 服 × 100 bot）就会超。
  - 写盘时持有预算锁：某个日志写盘卡住，判失败与停进程都要等这把锁。
  - bot 不登记进程台账，停任务又不再按 pid 收 bot：构建被强杀后留下的 bot 再没有路径收掉。

## 决策
1. **管道 + 有界泵，两级预算语义不同**：bot 与钩子后台进程的 stdout / stderr 合流走管道，由插件内的泵线程按字节计数后写日志，泵始终读到管道 EOF。
   - 单个日志（默认 64 MiB）到上限只截断这一个日志：写一行 `[OUTPUT_LIMIT] limit=per-sink` 标记，之后的输出读出来丢掉，构建结束时告警；不判失败、不停进程。
   - 整次构建（默认 1 GiB）到上限写 `[OUTPUT_LIMIT] limit=run` 标记，判失败并停掉全部受监管进程。
   - 两道上限可调，上界 16 GiB。日志个数与受监管进程数不设固定上限。
   - 计数全用原子操作，写盘不持有任何共享锁；整次构建的额度里留出一小块给标记行，越限记录本身不会被挤掉。
2. **构建级共享服务持有预算与监管**：每个顶层构建一份 `RunOutputService`（Gradle BuildService，配置缓存复用时也是新的一份），所有任务共用同一预算。
   - 监管器只认本构建自己起的进程及其子孙进程（`ProcessHandle` 记着启动时刻，防 pid 复用）。子孙进程靠定时扫一遍本 JVM 的进程树、沿父进程链归属，不对每个登记进程各扫一遍进程表。
   - 监管器负责监管期限（由场景结果等待上限推出，见 FR-32）、非零退出、管道被子孙进程继承、构建结束仍未收尾等判定。失败是粘性的、先到先得，原因收敛成有界的 ASCII 文本。
   - 钩子拿不到预算时拒绝启动外部命令，不退回无上限写盘。已判失败后普通进程拒绝启动，场景后钩子起的收尾进程照样启动。
3. **结果目录的输出所有权记录 `output-run.state`**：接手时写 `RUNNING` 与跑这次构建的 JVM（`owner=<pid>@<启动毫秒>`）；收尾时写 `CLOSED_OK` / `RUN_FAIL`、计入预算的字节数、失败原因，以及收尾期限到时仍存活的受监管进程（`live=`，无法确认时为 `live=unknown`）。
   - 下一次构建**只在上一次可能仍有进程在写时拒绝接手**：`RUNNING` 的持有者仍存活且不是当前 JVM；`RUNNING` 的持有者已结束（或就是当前 JVM），但进程台账里还有身份核对得上、仍存活、又不归本构建监管的 bot 或钩子进程；`RUNNING` 没有可用的持有者（旧格式、为空或读不懂）、`live=unknown`、没有 `live=` 记录的旧格式、所列进程仍存活、或记录读不懂。上一次失败但其进程都已确认结束，或没收尾就结束、台账里也没有它的存活 bot 与钩子进程时，只告警、照常接手。
   - 拒绝时不改写记录，报错按恢复办法给出步骤：有存活进程时跑 stop 任务（`stopE2eProcesses` 或对应的 `stop<场景>Cluster` 等），之后的构建自己接手；持有者还在跑时等它结束；无法确认时（没有持有者的 `RUNNING`、`live=unknown` 等），确认没有进程还在写后删除该文件。
4. **只有起进程、读判定的任务接手结果目录**：停任务（`stopE2eProcesses`、`stop<场景>Cluster`、`stop<场景>Stress`、`stop<名字>Serve` 等）与场景后的清理任务不接手、不写记录，也不受接手检查拦截，只用同一份预算去停本构建的进程。
5. **停任务跨构建收尾**：bot 与钩子进程起来时登记进程台账（`bot/<日志 key>`、`hook/<pid 文件相对结果目录的路径>`），与服务端 / 代理同一本台账。停任务依次：
   - 让监管器停掉本构建起的 bot；
   - 按 pid 文件收服务端与代理；
   - 按台账收之前的构建留下的进程：本构建仍在监管的跳过，其余核对命令与启动时刻后连同子孙进程一起收；
   - 收掉 `RUN_FAIL` 记录里 `live=` 列出、pid 与启动时刻都对得上的进程。记录本身不动，下一次构建确认所列进程都已结束后自己接手。

   固定名任务 `stopE2eProcesses` 不论声明了哪些拓扑都注册，只做后两步，不按 pid 文件停；同一条命令里的场景、钩子与 serve 任务都排在它之后。直连场景的前台服务端同样登记台账（`backend/<名字>`），等结果时被取消或出错都连同子进程收掉。

   场景与 serve 的收尾只停本构建起的 bot，不因别的 bot 判失败。按 pid 文件收尾的钩子（`StopPidHook`）遇到不是本构建起的进程时同样按台账核对，对不上的不碰。

## 理由
- 只有经 JVM 手的输出才能计数和中断；内核直写下，任何事后清理都晚了。
- 磁盘安全只需要整次构建一道闸。单个日志过大是排障体验问题，不是正确性问题：截断并告警就够，判失败会把安全阀做成默认失败，还会连带停掉正在正常跑的进程。整次构建超限则意味着磁盘安全边界已到，必须全部停下。
- 预算放在构建级而不是任务级：一次构建里多个任务、多个进程叠加才是事故形态，各任务各自设上限仍会被乘法放大。
- 日志个数不设上限：它由 DSL 声明的 bot 与钩子数量决定，每个只占一个 8 KiB 缓冲与一个泵线程；字节总量已由整次构建上限兜住，个数上限只会让大规模压测在运行期崩掉。
- 写盘不持锁：防「管道写满导致子进程永久阻塞」的设计目标，不能被某个卡住的写盘反过来拖住判失败与停进程。
- 所有权以「是否还有进程可能在写」为判据，而不是「上一次是否成功」：上一次的失败已由那次构建自己报告；场景结果文件每次开跑前都会清掉，结果读不到就判失败，不会把上一次的结果当成本次的；真正的隐患只有并发写入。
- 拒绝时保留记录：被拒的构建若改写记录，下一次构建看到的就是「被拒」而不是原隐患，隐患会被洗掉；两个构建同时跑时，后来者也不会冲掉先来者的所有权。
- 停任务不接手：它们的职责正是消除「还有进程在写」这个隐患，拦住它们就把自救的路堵死了；它们不读判定，也就不需要所有权。
- 存活进程按 pid + 启动时刻记录：下一次构建可以自己确认它们是否已经结束，停任务可以只杀确实是那个进程的 pid，而不必一律等人工处理。
- bot 与钩子进入进程台账：pid 文件会被下一轮覆盖，只认 pid 又会在 pid 复用时误杀；台账记着命令与启动时刻，是服务端 / 代理已经在用的跨轮收尾机制，bot 与钩子没有理由例外。连同子孙进程一起收，是因为钩子在 Windows 上经 `cmd /c` 起，只杀根进程会留下真正干活的子进程。
- `RUNNING` 记下持有者：构建被强杀后记录停在 `RUNNING`，只看记录分不清「另一个构建正在写」和「那次构建已经死了」，只能一律拒绝、等人手工删文件，连跑矩阵时一格被强杀，后面各格全部卡在准备阶段。记下跑构建的 JVM（pid + 启动时刻，防 pid 复用）后：持有者还活着，就是另一个构建在用，必须等；持有者已结束，往结果目录写日志的只剩它起的 bot 与钩子进程，它们都带着身份登记在台账里，台账里没有存活的就可以安全接手，有就交给 stop 任务收掉。一个 Gradle 守护进程同时只跑一个构建，持有者就是当前 JVM 时那次构建必定已经结束。接手判定只看台账里的 bot 与钩子进程：输出预算管的是它们写进结果目录的日志；残留的服务端与代理占着端口，起服前的端口预检会拦下并给出收尾任务。
- 固定名 `stopE2eProcesses`：只有直连场景的工程原本没有任何 stop 任务，被拒之后无路可走。它只认带身份的台账与状态记录，不按 pid 文件停：之前的构建留下的 pid 文件可能已指向复用了该 pid 的无关进程。同一条命令里的场景与 serve 排在它之后：它们起的服务端与代理不归进程监管、台账身份又对得上，并发跑就会被当成残留停掉。

## 后果
- **破坏性**：整次构建的 bot / 钩子输出合计超过 1 GiB，以前不失败、现在失败；单个日志超过 64 MiB 的部分不再落盘（不判失败）。输出量大的消费方需调高上限。
- 构建被强杀时记录停在 `RUNNING`：台账里没有它留下的存活 bot 与钩子进程时，下一次构建告警后接手；有则拒绝，跑一次 `stopE2eProcesses`（或对应的 stop 任务）后自己接手。上一次失败且记录了仍存活的进程时，同样跑一次 stop 任务即可。只有旧版本写下的 `RUNNING`（没有持有者）与 `live=unknown` 仍需确认后手工删除 `output-run.state`；取不到 JVM 启动时刻的平台写不出持有者，这样的记录同样按无法确认处理。
- 持有者还活着时一律等待：构建早已结束、只是守护进程没退又没写下收尾记录时，需要先 `./gradlew --stop`。
- `live=` 最多记 64 个进程，超出按无法确认处理；状态文件超过 4 KiB 就不是本插件写的，拒绝接手。
- 进程台账的读写在本 JVM 内互斥；每起一个 bot 或钩子进程改写一次台账文件。收尾时不清台账：同一 key 重复登记会覆盖旧记录，已结束进程的记录由停任务清理。
- 服务端日志不在本预算内（仍由服务端进程自己写文件），是已知缺口，另行处理。
- 契约（配置项、失败原因、状态文件格式与接手规则）见 [`API.md`](../API.md) §3.7，工作规格见 [`fr-34-bot-output-budget.md`](../specs/fr-34-bot-output-budget.md)。

## 备选方案
- **保留 appendTo，构建结束后再查文件大小**：越限时磁盘已经写满，落选。
- **按任务各自计数**：多任务叠加仍可乘法放大，落选。
- **单个日志越限即判失败并停掉全部进程（初版）**：正常负载就会触发，一个话多的 bot 拖垮整次构建，落选。
- **只停超限的那一个进程**：会把场景判定变成「日志写得多的 bot 中途消失」，与只截断日志相比没有额外的安全收益，落选。
- **固定日志 / 进程个数上限（初版 128 个）**：压测示例就会超，而且在运行期才暴露，落选。
- **上一次不是 `CLOSED_OK` 就拒绝（初版）**：一格失败连坐后续所有构建，连跑矩阵实测不可用，落选。
- **停任务也接手结果目录（初版）**：被拒之后连清理都做不了，落选。
- **停在 `RUNNING` 就一律拒绝、只能手工删状态文件（初版）**：连跑矩阵时一格被强杀，后面各格全部卡住，落选。
- **只看 `RUNNING` 的持有者是否存活**：持有者死了但它起的 bot 还在写，照样会并发写同一目录，落选。
- **不记录、每次无条件接手**：被中断构建的残留进程会和本次构建并发写同一目录，落选。
- **按目录加文件锁**：只能防同时运行的两个构建；锁随构建 JVM 退出而释放，防不了「构建已死、子进程还活着」，落选。
- **停任务按 pid 文件收 bot（旧做法）**：pid 文件不带身份，pid 复用时会误杀无关进程，改走带身份核对的台账，落选。
